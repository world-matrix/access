# 已知风险与规避

按「会不会把用户机器搞成砖」排序。

---

## 🟢 R1 — 收缩分区失败或损坏数据（已实测降级）

**风险**：`Resize-Partition` 被不可移动文件阻挡，或收缩过程中断电导致 NTFS
元数据损坏。这原本是整个项目唯一可能直接毁掉用户数据的步骤。

**实测结果（2026-08-23，目标机 D:）**：

```
SizeMin 69.4 GB   SizeMax 118.2 GB   最多可释放 48.8 GB
```

D: 已用 69.3 GB，收缩下限 69.4 GB，**两者几乎重合**——卷尾没有不可移动文件，
也没有严重碎片。需要 8 GB，余量 6 倍。风险等级由 🔴 降为 🟢。

这验证了「收缩 D: 而不是 C:」的决定：D: 是纯数据卷，没有页面文件、休眠文件和
MFT 保留区，这几样正是 C: 上典型的收缩阻挡物。

**规避**（仍全部保留，因为要适配用户的其他机器）：
1. 部署前**强制要求**用户有一份可用的外部备份，UI 上做硬性勾选确认
2. 收缩前自动预处理，全部可逆并记录原始状态：
   - `powercfg /h off` 关休眠
   - 页面文件移到其他卷或临时关闭
   - `vssadmin delete shadows` 清卷影（需用户确认，会删掉系统还原点）
   - `defrag C: /X /H` 整合可用空间
3. 用 `Get-PartitionSupportedSize` 探测真实可收缩下限，绝不盲目下命令
4. 收缩量 = `min(用户请求, 支持下限余量 - 10 GB 安全垫)`
5. 全程写操作日志到 `%ProgramData%\KLA\deploy.log`，失败时按日志逆序回滚
6. 只在**没有 BitLocker 加密**或已挂起保护的情况下操作

> 目标卷是数据卷时，第 2 步的预处理大多是空操作（数据卷上本来就没有页面文件和
> 休眠文件）。但部署向导仍要按流程探测，因为不能假设用户选的一定是纯数据卷。

## 🔴 R2 — 引导项写坏导致无法开机

**风险**：把 `Boot0000` 改成 KLA GRUB 后，若 GRUB 有问题则两个系统都进不去。

**规避**：
1. **绝不删除或修改 Windows 原有的 `Boot####` 项**，只新增
2. 修改 `BootOrder` 前，把原始 `BootOrder` 字节备份到
   `%ProgramData%\KLA\bootorder.bak`。格式与读写都由 `scripts/KlaFirmware.ps1`
   的 `Save-BootOrderBackup` / `Get-BootOrderBackup` 独占——部署侧和还原侧各写
   一份解析的话，格式一改就对不上，而对不上的正是最不能失效的那条路径。
   该备份**默认不覆盖**：第一次存的才是「部署之前」，部署后再存一次就把它盖没了。
3. GRUB 的 Windows 项用 `chainloader` 直接指向 `bootmgfw.efi`，
   不依赖 BCD，Windows 更新也不会破坏
4. 部署完成后**强制走一次验证重启**：设 `BootNext` 进 GRUB，确认菜单能显示、
   两个入口都能进，再把 `BootOrder` 改成 KLA 优先
5. 提供 `scripts/Restore-BootOrder.ps1` 一键还原 —— **已实现**：
   - 默认从 `bootorder.bak` 还原；备份丢了/没部署过，用 `-WindowsFirst` 应急，
     它只把现有的 Windows 项挪到最前，不新增任何项，比还原更保守
   - 写之前四道闸：备份非空、长度偶数、目标顺序里的项还存在（全不存在则拒绝）、
     **目标顺序里必须有 Windows 启动管理器**（没有则拒绝，除非 `-Force`）
   - 写完**读回逐字节比对**。有些固件会静默拒绝或截断写入，只看 API 返回值不够
   - 还原前先把*当前*顺序快照到 `bootorder.pre-restore.bak`，还原这一步本身也可撤销
   - 顺手处理 `BootNext`：它若指着一个已不在还原后顺序里的项（多半就是 KLA），
     改指 Windows。否则「还原完了下次开机还是进 GRUB」，用户会以为没生效
   - 支持 `-WhatIf`，先看会改成什么样再动手
   - **不删除 KLA 自己的 `Boot####`**。不在 `BootOrder` 里就不会被启动，
     留着几百字节 NVRAM 换来「以后重新启用不必重建」，也避免引入一个
     删除固件变量的危险原语（`KlaFirmware::Write` 刻意拒绝空写，
     因为 UEFI 里长度为 0 的写入等同于删除）
   - ⚠ **前提是还进得去 Windows**——它是个 PowerShell 脚本。GRUB 坏到连菜单都
     出不来时，先开机按 F12 / F9 / Esc（各家不同）调出**固件启动菜单**手选
     Windows Boot Manager 进系统，再跑本脚本。固件启动菜单是硬件级的，
     不依赖 `BootOrder`，永远救得回来。这条要写进 UI 的部署完成页。
6. `scripts/Test-KlaFirmware.ps1` 用合成字节流覆盖 `ConvertFrom-LoadOption` 和
   `Get-BootOrderBackup` 的正常/异常两侧（空描述、中文描述、非文件型设备路径、
   截断输入、空文件、奇数长度……）。**不需要管理员权限**，改完引导相关代码先跑它。
   这两个函数解析歪了不会抛异常，只会给出一个看着合理的错误结果然后被写进固件。

## 🟠 R3 — Secure Boot 阻止 Linux 启动

**风险**：Secure Boot 开启时未签名的 `grubx64.efi` 会被固件拒绝。

**规避**：
- 使用 Debian 的 **shim**（微软已签名）+ 自建 MOK 密钥签名我们的 GRUB 和内核
- MOK 注册**必须**用户在重启后于 MokManager 蓝屏界面手动确认，这是 UEFI 的
  物理在场验证，无法绕过。UI 里要提前用图示告知用户会看到什么、该按什么
- 降级路径：检测到用户不愿注册 MOK 时，提示可关闭 Secure Boot，或改用
  微软签名的 WinPE 方案（需回退到最初的技术路线 A）

## 🟠 R4 — 存储空间不足

**风险**：备份写到一半空间耗尽，静默失败。用户以为有备份，真要还原时才发现没有。

**实测约束**：目标机 238.5 GB，C: 剩 45.7 GB，D: 剩 48.9 GB，全盘自由空间
94.6 GB。原计划的 60 GB 隐藏分区不可行，已改为 **1 GB 固定分区**（只装救援
系统）+ `D:\KLA\` 以文件形式存镜像和备份链。

备份用文件而非独立分区，顺带消掉了「分区预分配的空间用不满就浪费、用满了
又扩不了」这一整类问题——文件方案下备份用多少占多少，删了立刻释放。

**规避**：
1. 部署向导按 C: 实际已用量 × 压缩比经验值估算母盘大小，给出推荐范围而非
   拍脑袋的固定值
2. 母盘默认用 **L2 范围**（排除用户 profile 数据），比 L1 省 10 GB 以上
3. 每次备份**开始前**检查剩余空间，不足则拒绝启动并明确提示，绝不半途失败
4. 保留策略自动执行，超配额时按最旧的整条链删除
5. L1 全量备份默认引导用户放外置盘

## 🟠 R4b — 目标机器没有 WinRE 可依赖

**风险**：`reagentc /info` 显示 WinRE 状态 Disabled，磁盘上也没有恢复分区。
原先「还原后委托 WinRE 跑 bcdboot 重建引导」的方案没有委托对象。

**规避**：改为连 ESP 一起捕获还原（backup-design.md §6）。因为还原目标是同一批
物理分区、GPT 分区 GUID 不变，捕获时的 BCD 引用还原后依然有效，不需要重建。

还原 ESP 时**只覆盖 `EFI\Microsoft\`，保留 `EFI\KLA\`**——否则恢复出厂会把
KLA 自己的引导删掉。

## 🟡 R5 — 增量链断裂

**风险**：用户删掉链中间的 WIM，后续所有还原点静默失效，直到真要还原时才发现。

**规避**：
- UI 把链渲染成有向时间线，依赖关系可见
- 删除时计算并明确列出「将连带失效的 N 个还原点」
- 定期后台 `wimlib-imagex verify` + sha256 比对，发现断链立即告警
- 每月起新链，限制单链长度不超过 8 个增量

---

## 🟡 R6 — Windows 更新破坏部署

**风险**：功能更新可能重建 ESP 内容、重置 `BootOrder`、或重新创建 WinRE 分区。

**规避**：
- KLA 文件放在 `EFI\KLA\` 独立目录，Windows 不会动
- Kla.App 注册一个登录时运行的轻量检查任务，发现 `BootOrder` 被改回则提示
  用户一键修复
- 不占用 WinRE 分区，避免与 `reagentc` 冲突

---

## 🟡 R7 — 硬件兼容性

**风险**：新款笔记本的 WiFi/有线网卡、NVMe 控制器、显卡在 Debian 稳定版内核上
没有驱动，进了 ACCESS 上不了网或看不到硬盘。

**规避**：
- 基线用 **Debian 13 (trixie)**，内核较新
- 打包 `non-free-firmware` 全量固件（Intel/Realtek/Broadcom/MediaTek/Atheros）
- 需要更新硬件支持时切 backports 内核
- 部署向导在 Windows 侧先枚举本机网卡/存储控制器 PCI ID，与 ISO 内的驱动
  清单比对，**部署前**就告知兼容性风险，而不是等用户救援时才发现

## 🟠 R7b — 为压到 1 GB 而做的裁剪砍过头

**风险**：为达成 1 GB 预算，构建时删掉了大量内核模块、固件和语言包
（见 architecture.md「体积预算」）。删错一类，后果是**进了救援环境看不到
硬盘、或者上不了网**——恰好是最需要它的时候失效，且要到真出事那天才发现。

**已做的边界划定**：

| 区域 | 处置 | 依据 |
|---|---|---|
| 存储（scsi/ata/nvme/usb/mmc） | **一个不动** | 看不到硬盘 = 救援归零 |
| 网卡（net/wireless/ethernet + 全部网卡固件） | **一个不动** | 用户明确要求「自动装网卡驱动」 |
| 主力文件系统（ext4/xfs/btrfs/ntfs/vfat/exfat） | **一个不动** | 挂不上就读不出数据 |
| 声卡、电视卡、InfiniBand、ISDN、业余无线电 | 删 | 救援场景无关 |
| 独显驱动 + GPU 固件（amd/nouveau/radeon） | 删 | 回落 EFI framebuffer 仍可显示 |
| 集群文件系统（ocfs2/gfs2） | 删 | 单机救援用不到 |

**规避**：
1. 删模块后**必须 `depmod -a`**，否则 `modprobe` 会去找已不存在的 `.ko`
   （已写进 `9010-kla-slim.hook.chroot`）
2. `--firmware-chroot false` 是硬要求——为 `true` 时 live-build 会把归档区
   所有 `firmware-*` 包自动塞回来，200 MB 的裁剪瞬间失效
3. 阶段 1 验收清单里**必须**包含：在真机上启动 ACCESS，确认
   (a) `lsblk` 看得到 NVMe 全部分区、(b) 有线和无线都能连上、
   (c) `wimlib-imagex --version` 可执行、(d) 中文文件名显示正常
4. 独显机器的图形回落只做过推理未做实测，遇到时按需做一个加回
   `firmware-amd-graphics` 的 "full" 构建变体

> 已知取舍：救援环境**没有声音**，独显机器**没有硬件加速**。
> 两者都不影响救援本身，但要在文档里写明，免得当成 bug 排查。

## 🟡 R8 — VSS 快照失败导致备份不一致

**风险**：不走卷影副本直接捕获运行中的系统，注册表 hive 和数据库文件会不一致，
还原出来的系统可能起不来。

**规避**：
- 一律使用 `wimlib-imagex capture --snapshot`
- 捕获前检查 VSS 服务状态和可用空间（VSS 需要卷上有余量存差异数据）
- 捕获后 `wimlib-imagex verify` 校验
- 首次创建出厂母盘时，UI 建议用户先跑 `sysprep /generalize`（可选，
  跳过则母盘绑定当前硬件）
